## Summary

Phase 6 adds the axe accessibility suite, designed root 404 and error pages, a shared EmptyState primitive with an empty-state audit across public and admin surfaces, a non-blocking Lighthouse CI job with recorded local medians, and the deploy runbook, clip shot list and case study. The quality is generally high: the error pages follow the Next.js 16 bundled docs (the `retry` prop, self-contained `global-error` with its own `<html>`, `<title>` as a React element), design tokens are respected everywhere including the inline-styled global error page, the case-study numbers match the committed Lighthouse evidence JSONs, the runbook's Supabase flags check out against the CLI help, and lint, typecheck and all 44 unit tests pass. The one substantive gap is acceptance criterion AC-1: the axe suite never sees the signed-in admin inbox or a lead detail page, only the bounced sign-in redirect, yet build plan step 2 is ticked as satisfying AC-1.

## Major

### 🟠 AC-1 admin coverage is not met; only the sign-in bounce is axe-checked, `e2e/axe.ci.spec.ts:48-64`
**Problem**: AC-1 requires the axe spec to check "the admin inbox and one admin lead detail". The existing CI admin pattern (`e2e/admin.ci.spec.ts`) never completes OTP, so the new axe spec substitutes two tests that both land on the sign-in page: a direct visit to `/admin/sign-in` and a bounce off `/admin/inbox` that asserts the redirect and then scans the sign-in page again. The authenticated inbox (including the new EmptyState and the filter form) and the lead detail page are never scanned. Build plan step 2 in `docs/specs/phase-6.md` is marked `[x]` claiming AC-1 is satisfied.
**Why it matters**: The admin desk is half the product and its list/detail surfaces got new UI this phase (EmptyState, filter-aware copy). The permanent regression guard the phase promises does not cover them, and the spec now records a tick the code cannot back. The in-code comment is honest, but the AC and the plan tick are not.
**Suggested fix**: Either amend AC-1 and the build plan note to state that admin axe coverage in CI is limited to the unauthenticated bounce (and record signed-in admin a11y as a manual or deferred check), or give the suite a CI-capable sign-in path (for example a test-only OTP bypass or a seeded session helper) and scan `/admin/inbox` plus one lead detail for real. Do not leave the tick claiming full AC-1 coverage.

## Minor

### 🟡 Global error page duplicates the recovery links instead of reusing the component, `app/global-error.tsx:72-124`
**Problem**: The three recovery links (home, call, book) are re-implemented with inline styles, duplicating `components/site/recovery-links.tsx` almost link for link. `global-error.tsx` already imports `./globals.css`, so the Tailwind classes used by `RecoveryLinks` (and used by `app/error.tsx` on the same links) would work here too.
**Why it matters**: Two hand-maintained copies of the same recovery UI will drift the first time a label, phone number style or link target changes; the phase's own goal was one pattern per surface.
**Suggested fix**: Render `<RecoveryLinks />` inside `global-error.tsx` and keep only the genuinely necessary inline styles (body flex shell) in the file.

### 🟡 Runbook search step depends on `rg`, which the operator may not have, `docs/deploy.md:86`
**Problem**: The post-deploy verification block runs `rg -i "service_role|service-role" .next || echo "clean"`. `rg` (ripgrep) is a third-party tool not present on a default Windows or macOS machine, while AC-4 states every command in the runbook is copy runnable.
**Why it matters**: The human executing the runbook hits a command-not-found right at the security-critical check (no service-role key in the client bundle); `|| echo "clean"` then masks it as a pass if someone only reads the output loosely.
**Suggested fix**: Use a portable search (for example `node -e` with `fs` scanning `.next/static`, or `findstr`/`grep` with a note), or state the `rg` prerequisite at the top of the section.

### 🟡 Checklist tick claims a "live production build" while deploys are still pending, `docs/PLAN.md:269`
**Problem**: The demo-honesty checklist item is ticked with evidence "(live production build: fictional notice, ...)". The staging and production deploys (phase-6 build plan steps 10 and 11) are still unchecked, so what was actually verified is a local production build, not a live URL.
**Why it matters**: Demo honesty is a hard project rule and the checklist is the launch gate; wording that overstates the evidence invites the human to believe a live-URL check already happened.
**Suggested fix**: Rephrase the tick to "local production build" and leave the live-URL confirmation to the AC-6 step after the production deploy.
