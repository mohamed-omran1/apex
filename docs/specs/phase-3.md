
# Phase 3. Booking flow

**Date**: 2026-10-15
**Status**: In Progress (plan approved 2026-10-15)

## Summary

Phase 3 turns `/book` from a placeholder into the working booking flow: a Zod schema shared by the form and the action, a single Server Action that validates, checks the zip, guards duplicates, inserts the lead and sends both emails, and the form UI built to the booking frame. Spam is covered by a honeypot, server side Zod, an in memory rate limit, and Turnstile code that activates only when keys exist. The gate is a live submit that lands a `new` lead in the database and an owner email that arrives.

## Context

Phases 0 to 2 shipped the scaffold, the static pages and the database with RLS. The booking flow is the product: PLAN.md's own line is that a contractor demo lives or dies on the booking flow and the admin view. The schema already holds everything this phase needs (consent columns, `reference_code`, phone index, free text `lead_events.event_type`), so this phase writes no migration.

Four forces shaped this spec:

1. **Phase 2 left three decisions open** and this spec settles them: the duplicate guard mechanism (anon cannot select leads), the location of the rate limit, and the insert rule (the lead action generates its own reference code and stays `.select()` free).
2. **The repo rule on the service role key** is strict: it never appears in the repo, the client or chat. The plan says the key stays on the server. This spec puts it in `.env.local` only, used inside the Server Action for exactly two calls: the duplicate phone lookup and the `lead_events` inserts. The lead insert itself stays on the anon key so RLS keeps enforcing `status = new`.
3. **Turnstile needs a Cloudflare account** that does not exist yet. The verify code ships now but runs only when both Turnstile env keys are present, so activation later is a config change, not a code change.
4. **Design and plan disagree on out of area zips.** The frame shows a blocking error; PLAN.md promises "a polite message and a way to leave a number anyway". This spec follows the plan: warning plus tap to call, submit stays enabled, and the admin can decline. The emergency short form never gates on zip at all.

Email reality: Resend sends only with an API key and a verified from address. Without both, the action skips sends, logs nothing, and the submit still succeeds. The owner email is the step that protects the owner from missed leads, so a send failure is recorded as a `lead_events` note and the visitor still sees success; the lead is already saved.

## Requirements

**User stories**:
- As a visitor on a phone, I can request service in under a minute and get a reference code back.
- As the owner, every request arrives in email with a tap to call link, and a double submit from the same number does not create a second lead.
- As the site operator, bots and scripts get no foothold: honeypot, validation, rate limit, and Turnstile when configured.

**Acceptance criteria**:
- **AC-1**: `/book` renders the flow from the booking frame: steps rail, kind picker, field set that changes with kind (emergency is the four short fields), window chips, inline error states and a success state showing the reference code. Mobile stacks to one column. Only design tokens, no hard coded colors or fonts.
- **AC-2**: One Zod schema in `lib/validation/lead.ts` is imported by both the form (client pre validation) and the action (authoritative check). Vitest covers the emergency variant, the full variants, estimate requiring address, membership via `?type=membership`, bad phone, and missing window.
- **AC-3**: A valid submit inserts exactly one `leads` row with `status = new` and a reference code generated by the action (`APX-` plus six characters, retry on unique collision). The action contains no `.select()` after the insert. Consent flag, `consent_at`, `consent_version = v1` and UTM fields persist. The insert runs on the anon key so RLS enforces the status.
- **AC-4**: A second submit from the same normalized phone within 10 minutes creates no new lead: the action appends a `lead_events` row to the existing lead (service role) and returns the existing reference code with a duplicate message. The lookup compares digits only, so `(214) 555-0100` and `2145550100` match.
- **AC-5**: Each successful submit sends an owner alert (subject prefixed `URGENT` for emergencies; body has kind, contact, tap to call link, reference code and admin lead link) and a visitor receipt when an email was given (transactional regardless of marketing consent, carries the fictional demo notice). Each send writes an `email_sent` `lead_events` row with to and subject in metadata. When `RESEND_API_KEY` or `RESEND_FROM` is missing, sends skip with a console warning and the submit still returns success.
- **AC-6**: Honeypot filled returns a fake success and inserts nothing. A third submit from the same phone inside 10 minutes (or a sixth from the same IP inside 10 minutes) returns `rate_limited` with no insert. Turnstile is verified with the siteverify endpoint only when `TURNSTILE_SECRET_KEY` is set; without it the step no-ops.
- **AC-7**: An out of area zip shows the polite warning with a tap to call link while the submit button stays enabled; the action re checks the zip server side, records the zip as typed and never blocks on it. The emergency form submits regardless of zip.
- **AC-8**: Playwright tests tagged `@ci` run in GitHub Actions green with no database writes (render, client validation errors, kind switching, zip warning, honeypot hidden, chips semantics). The local gate runs one full submit against the linked project: the row exists with status `new` and the owner email arrives in the real inbox.
- **AC-9**: Gate passes: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`, `npm run test:e2e`. The browser bundle contains no Supabase service role key or supabase client for writes (`git grep -i service_role` empty, `.env.local` uncommitted). Advisors unchanged (no migration ran).

## Options considered

### Duplicate guard (required by Phase 2 follow-up)

**Option A: service role key, server only.** The action holds a second client with the service key for the phone lookup and event inserts.

**Option B: narrow anon policies.** A migration adds anon select on leads by phone window plus anon insert on lead_events.

**Option C: SECURITY DEFINER function.** Anon executes a function that does the lookup internally.

Chosen: **A**. B leaks full lead rows to anyone who probes a phone number. C adds a public database endpoint that needs its own review. A matches PLAN.md's "the service-role key stays on the server" and needs no migration. The cost is one long lived secret in `.env.local`; the blast radius is one project, and the repo rules keep it out of git, the browser and chat.

### Out of area zip

**Option A: warning, submit enabled** (plan's promise). **Option B: blocking error** (the frame).

Chosen: **A**, with the frame's error styling reused as the warning. Blocking would break the plan's "leave a number anyway" and the services FAQ that promises exactly that. Emergency never gates.

### Rate limit location

Chosen: **in memory per instance inside the action** (3 per phone, 6 per IP, 10 minute window). Platform level rules (Vercel WAF) are the production answer and are recorded as follow-up; in memory is honest for a single instance demo and needs no new service.

## Decision

Build the flow in one Server Action with a shared Zod schema, service role confined to duplicate guard and event writes, keyless Turnstile wiring, split E2E (form only in CI, full submit local), no migration.

**Implementation skills**: `supabase`, `supabase-postgres-best-practices`, Next 16 bundled docs before any Server Action code, Resend docs (`/llms.txt`) before the email layer.

## Feature design

**Routes and files**:

```text
app/(public)/book/page.tsx          server: fetch active zips + site phone, render shell
components/book/booking-form.tsx    client: useActionState, kind picker, validation, chips
lib/validation/lead.ts              zod: leadFormSchema (discriminated by kind)
lib/supabase/server.ts              anon factory (reads, insert) + service factory (action only)
lib/email/resend.ts                 client wrapper, null when unconfigured
lib/email/templates.ts              ownerAlert(), visitorReceipt() -> {subject, html, text}
actions/submitLead.ts               the only write path
e2e/booking.ci.spec.ts              @ci form only suite
e2e/booking.full.spec.ts            @local full submit (excluded by grep in CI)
```

**Action contract** (`actions/submitLead.ts`, invoked via `useActionState`):

```ts
type LeadFormState = {
  ok: boolean
  code: "submitted" | "duplicate" | "rate_limited" | "invalid" | "server_error"
  referenceCode?: string
  fieldErrors?: Record<string, string>
  message?: string
} | null

submitLead(prev: LeadFormState | null, formData: FormData): Promise<LeadFormState>
```

Order of operations, each step short circuits with the state above:

1. Honeypot `company` filled: return `ok` with a plausible `APX-` code, insert nothing.
2. Turnstile verify when `TURNSTILE_SECRET_KEY` set: POST siteverify, failure returns `server_error` with a retry message.
3. Rate limit check (module scoped `Map`, keyed by normalized phone and by client IP from `x-forwarded-for`): over limit returns `rate_limited`.
4. Zod parse: failure returns `invalid` with `fieldErrors` in English, matching the frame copy ("Name is required.", "Add a phone number so the owner can call you back.").
5. Zip check: fetch active `service_areas.zip_codes` with the anon client, compare in code. Out of area never blocks (AC-7); the result is only recorded.
6. Duplicate guard (service client): fetch leads created in the last 10 minutes (`created_at > now() - interval '10 minutes'`), filter in code on digit normalized phone. Hit: insert `lead_events` (`event_type = duplicate_submission`, body summarising the resubmission, metadata with the new payload) and return `duplicate` with the existing reference code.
7. Generate `reference_code` (`APX-` + 6 chars from `crypto.randomBytes`, collision retry up to 3 times against the unique index), insert with the anon client, **no `.select()`**.
8. Emails (best effort): owner alert always; visitor receipt when email present. Each success writes an `email_sent` event (service client). Owner send failure writes a `note` event with the error.
9. Return `submitted` with the reference code.

**Zod schema** (one definition, discriminated union on `kind`):

| Variant | Fields |
|---|---|
| `emergency` | name, phone, zip, issue (required); no address, day or window |
| `estimate` | email, address (required), preferred_day (optional, today or later), preferred_window (required) plus base |
| `repair`, `tune_up`, `membership_enquiry` | address optional, preferred_window required, preferred_day optional, plus base |
| base (all) | kind, name (min 2), phone (10+ digits US style), zip (5 digits), consent_email bool, consent_sms bool (always false in MVP), honeypot, UTM strings optional |

`preferred_window` is a literal union `asap | morning | afternoon | evening`, validated here, no enum in the database (Phase 2 decision). Consent: when `consent_email` is true, action sets `consent_at = now()` and `consent_version = v1`; otherwise both stay null.

**UI states** (from the frame, mobile stacks the rail above the form):

| State | Behaviour |
|---|---|
| Idle | steps rail shows zip, kind, details; kind picker four cards; fields per variant |
| Client invalid | submit blocked in the handler, inline errors in frame copy, focus first error |
| Zip warning | message under zip field with tap to call; button stays enabled |
| Submitting | button disabled, label "Sending..." |
| Success | success panel: reference code, what happens next, call link; form unmounted |
| `duplicate` | success panel variant: "We already have your request from the last ten minutes. Your reference stays APX-..." |
| `rate_limited` | message above form: "That is three requests in ten minutes. Please call instead." with phone link |

**Spam model**: honeypot (visually hidden, `tabIndex=-1`, `aria-hidden`, off screen), shared Zod, in memory rate limits, keyless Turnstile, plus the platform rate limit as follow-up.

**Emails**: plain HTML with inline styles, no remote images. Owner subject `URGENT: New lead APX-... (emergency, 75201)` or `New lead APX-... (repair, 75204)`. Admin link points at `${SITE_URL}/admin/leads/${id}` which 404s until Phase 4 (acceptable, recorded in follow-ups). Receipt carries "Apex is a fictional demo company" per the demo honesty rule.

**Test scenarios** mapping to ACs:
- Unit (Vitest): schema variants and edge cases (**AC-2**), rate limiter windows (**AC-6**), duplicate phone normalization (**AC-4**), reference code format (**AC-3**).
- E2E `@ci`: render, empty submit errors, kind switching, zip warning, honeypot hidden, chip semantics (**AC-1**, **AC-7**).
- E2E `@local` + manual: full submit, DB row, owner email (**AC-8**).

## Consequences

**Positive**:
- The one write path stays one file: validation, spam, duplicate guard, insert and email are all reviewable in `actions/submitLead.ts`.
- No migration means Phase 3 cannot regress the Phase 2 security gate.
- Turnstile activation later is two env vars.

**Negative / tradeoffs**:
- The service role key now exists in the developer's `.env.local`; a leak of that file is total. Mitigation: never committed, never in chat, used for two calls only.
- In memory rate limits reset per server instance and do nothing under serverless cold starts across regions; acceptable for a demo, not for production.
- If the owner email send fails, the visitor still sees success; the failure surfaces only as a `note` event until Phase 4's inbox shows it.

**Neutral**:
- The admin link in the owner email 404s until Phase 4.
- `membership_enquiry` has no picker card; it arrives via `?type=membership` from the membership CTA.
- CI e2e needs the two public Supabase env values (they are publishable by design), nothing secret.
